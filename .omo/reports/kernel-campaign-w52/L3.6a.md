## What changed

### S1 — borrowed request authority (mid-turn request.open/transition refused)
Root cause confirmed: the old `requestAuthorityKernel` in
`apps/openomni/src/composition/cluster-runtime.ts` borrowed the live
activation's owner+fence for the *commit*, but `row()` still reported the live
owner, so `ownsRequestRevision` (row.leaseOwner vs the caller's generated
`pid:request:*` owner) refused the decision → CommitFailed → ForeignFailure on
every mid-turn `request.open`/transition.

Fix (fail-closed): `requestAuthorityKernel` now lives in
`packages/agent/src/session-admission.ts` (exported via `packages/agent/src/index.ts`;
cluster-runtime.ts re-exports it so `apps/openomni/src/index.ts:~276` is unchanged
in shape). On a running session, `adoptFence` records the live owner+fence AND
the borrowing caller; `row()` masks `leaseOwner` to the borrowing caller only
(fence and revision are never masked — a rotated fence or moved revision still
refuses); `commitRequestTransition` substitutes the real live owner+fence. An
idle session falls back to real adoption (documented takeover). An unrelated
owner that never adopted through the view stays refused.

### S2 — foreign-session admission riding the sender's batch
Root cause confirmed: `commitSessionRequest` appended a `new_session` child's
admission (foreign sessionId) into the sender's single-session fenced batch;
`validActionBatch` refused with CommitRefused{"revision"} family errors.

Fix: the intake in `commitSessionRequest` drops an admission whose
`sessionId !== sessionId` — the child's own entity commits it through
`ports.inbox.commit` (which the gateway already calls unconditionally after
`openNativeRequest`). Same-session admissions still ride the batch atomically.

### S1 follow-through — idle-owner wake for out-of-turn answers
With S1 fixed, `request-channel-e2e` still hung: a ws `request_answer` on an
IDLE entity session committed the answer + reply intake fine (real adoption),
but nothing drained the session — the app-side `wake` doorbell is
process-runner-only ("entity sessions drain inside the delivering RPC", which
is true for messages but was false for this answer path). Fix in the owned
boot request port region of `apps/openomni/src/index.ts`: the `requests` port
now routes `answer` through the entity's own `RequestResolve` RPC when the
session is not running and not process-runner — the entity handler commits the
transition AND drains, so the woken turn runs before the ack. Running sessions
keep the borrowed-authority direct commit (a second RPC on a busy mailbox
would queue behind the very turn that may be awaiting the answer); process
runners keep direct commit + doorbell. This is exactly the seam
`session-requests.ts` documents: "on the entity plane these transitions route
through the entity instead".

## Remaining failure — NOT S1/S2 (out of lane, S4 family)
`message-terminal-boundaries.test.ts` "deadline-bound child delivers
interrupted under the original request" hangs (pre-existing at baseline,
identical 5s-timer + bun timeout signature; L3.3c-B had mapped it to S1+S2 —
that mapping was wrong for this variant; the result/error variants ARE S1+S2
and are now green).

Diagnosed root cause (code-traced, two independent confirmations):
`SessionEntityLive.receive` = appendReceived → `drain` (runs the FULL turn via
the runTurn port) → ack. So the parent's `send_message` tool
(`executeMessage` → `ports.inbox.commit` → `entityClient(child).Prompt`)
awaits the child's whole turn. The test's child model blocks on a release
promise that is only resolved AFTER `await ownerStart(...)` returns — but
ownerStart's ingest holds the parent turn, which holds the child Prompt RPC,
which holds the child turn: a structural deadlock. Evidence: the test times
out at 30s without ever reaching the 5s "missing child terminal" expect (it
never gets past `await ownerStart`), and teardown reports
`GenerationUnsettled: session gateway-ingress generation 1 has 1 live owner(s)`
(the hung ingest frame).

The fix requires the entity turn port to ack at the durable turn boundary and
run the remainder of the turn detached (session-controller.ts's own comment:
"this port only reaches the durable turn boundary"), i.e. changes in
`packages/agent/src/session-controller.ts` / `session-entity.ts` /
`apps/openomni/src/index.ts` entityPorts.bind — all outside this lane's owned
paths and colliding with concurrent lanes (L3.5 edits index.ts near the
deadline-arm fork). Left for the S4 lane with this analysis.
