## Finding 5 — unbounded ancestor scan (`inspect.ts:42-59`)

Fix: `ancestralTurnId` no longer takes one indexed `actionById` point read per
chain link. Ancestors are resolved from descending 256-action `historyPage`
windows (one bounded indexed range read per 256 links), memoized per page. A
one-action page over a 300-link chain now costs the page read plus at most
`ceil(301/256) = 2` window reads and **zero** point reads, and attribution
stays exact: a turn-less chain reports `turnId: null` because the walk reached
the root in memory, never because a budget truncated it.

Why not the brief's two literal alternatives:
- A nearest-turn-intent indexed fact alone is unsound: `inbox.deliver` actions
  carry a `turnId` and can commit **before** their turn's intent (proven by the
  existing ledger test "snapshot tails fold deliveries committed before their
  turn intent", `packages/ledger/test/session/bounded-reads.test.ts`), so "no
  turn intent below" does not imply "no turn-carrying ancestor below" — a
  null short-circuit there would reintroduce the r1 attribution bug.
- A hard ancestry budget shared with the page budget has no sound exhaustion
  behavior: truncating to null reintroduces the r1 bug, and shrinking the page
  livelocks the mandated one-action page (a `limit:1` page can never afford a
  2-hop walk; the existing multi-hop attribution test requires exactly that).
Bounded windows deliver the finding's actual demand — correct attribution AND
bounded lookup work — for both turn-less and turn-descended long chains. The
window walk stays inside one session by the ledger chain law
(`parentBelongsToSession`, `sqlite-l0-write.ts`).

Tests added (both count real kernel reads via `spyOn`):
- `a one-action page over a 300-link turn-less chain resolves null attribution
  in bounded window reads` — mirrors the r2 probe (configure + 300 causally
  linked message actions, `{depth:0, cursor:head-1, limit:1}`): asserts the
  returned action, `turnId` null, `actionById` called **0** times (was 300 in
  the review probe), `historyPage` ≤ 3 calls.
- `a one-action page over a 300-link chain under a turn attributes the turn in
  bounded window reads` — same shape rooted at `turn-1` via
  `fencedTurnFixture`: asserts `turnId === "turn-1"` (no truncation),
  `actionById` 0, `historyPage` ≤ 3.

Mutant proof (scratch, reverted): `let low = child.ordinal - 1` → `let low = 0`
(windows never fetched = truncation to null). The under-turn regression failed
with `Expected: "turn-1" / Received: null` (1 pass, 1 fail); after byte-exact
revert both tests pass (2 pass, 0 fail).

## Finding 7 — phase metadata read after the final consistency check (`gateway.ts:220-232`)

Fix: `readSessionCursor` captures **all** phase facts (`latestOpenTurn`, its
intent via `actionById`, and the genesis `latestAction(sessionId, 1)`) before
`after = kernel.row(...)` and the fence/revision check; `phaseFacts` is now a
pure function over a captured `PhaseSources` record and reads no kernel at all.
A commit interleaved during the phase reads moves the after-row revision and
surfaces as the promised typed `session_gap`; a commit after the check can no
longer leak a newer turn's timestamp into an old page. The `toolWallMs`
`actionById` reads after the check are immutable by-id reads of actions already
in the validated page and stay put.

Test added (`gateway-phase-since.test.ts`, the review's exact interleaving): a
kernel wrapper whose `latestOpenTurn` commits the turn-1 terminal (ts 60) and a
turn-2 intent (ts 900) before delegating; asserts the response is a
`session_gap` at the new head — never a `session_snapshot` pairing the old head
with `phaseSince: 900`.

Mutant proof (scratch, reverted): moved `const after = kernel.row(...)` above
the phase-fact capture (reintroducing the late read relative to validation).
The new test failed with exactly the reviewed defect —
`type: "session_snapshot", phaseSince: 900` instead of the gap (0 pass, 1
fail); after byte-exact revert the file's 3 tests pass.
